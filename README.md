# 🤖 Rber

> **Request software. Compare implementations. Select the best outcome.**

Rber is a vision for the future of software engineering.

Instead of assigning work to a single development team, organizations submit a software specification to a marketplace of implementation providers. AI agents, software factories, internal engineering platforms, and external vendors compete to deliver the best solution based on quality, security, compliance, cost, and delivery time.

The specification becomes the primary asset.

---

## Why Rber?

Traditional software development focuses on building software.

Rber focuses on selecting the best outcome.

Just as Uber connects riders with drivers, Rber connects software specifications with implementation providers.

```text
Business Need
      ↓
Specification
      ↓
Marketplace
      ↓
Competing Implementations
      ↓
Evaluation
      ↓
Best Solution Wins
      ↓
Production
```

---

## The Problem

Modern software engineering spends significant effort on:

- Estimating projects
- Allocating teams
- Managing capacity
- Coordinating implementation
- Reviewing code
- Tracking progress

As AI reduces the cost of implementation, the bottleneck shifts to:

- Understanding requirements
- Managing context
- Verifying quality
- Governing outcomes

## Deploy to GitHub Pages

The Pages workflow builds the static site and deploys it whenever changes are pushed to `main`. Before the first deployment, either open the repository's **Settings → Pages** and set **Build and deployment → Source** to **GitHub Actions**, or add a repository secret named `PAGES_TOKEN` containing a token with Pages write permission so the workflow can enable Pages. You can also start a deployment from the **Actions** tab with **Deploy to GitHub Pages → Run workflow**.

The published project site will be available at `https://richardabbuhl.github.io/ew26-rber/` after the first successful deployment.
